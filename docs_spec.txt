## 1. PROJECT OBJECTIVE AND PROBLEM STATEMENT
================================================================================
AICTE receives complaints about technical education institutions from students,
faculty, and other stakeholders. Different units handle them, notably the
Regulation Bureau (RB) and the Public Grievance Redressal Cell (PGRC). Cases for
the SAME institution may be handled by different units without visibility into
each other, causing duplicate effort, overlapping actions, delays, and unclear
ownership.

Build a centralized, real-time dashboard where authorized officials can:
- register and track complaints per institution,
- see which bureau is primarily responsible and which bureaus participate,
- detect potentially related complaints (explainable, deterministic, reviewable
  by humans, never auto-merged),
- keep full status/assignment/audit history,
- receive notifications and see overdue/escalation indicators,
- view analytics and export CSV reports, all derived from database records.

The prototype runs locally, needs no external services, and uses synthetic data.

## 4. SYSTEM ARCHITECTURE
================================================================================
  Browser (React SPA, Vite)
        | HTTPS/JSON, Bearer JWT, base path /api/v1
        v
  FastAPI app  -- middleware: request-id, structured logging, CORS, security headers
        |  routers (thin) -> services (business rules, authorization, audit)
        |  -> SQLAlchemy session (one transaction per request)
        v
  PostgreSQL (schema via Alembic; triggers for append-only tables)
        ^
  APScheduler job (in the API process): overdue scan, idempotent

Layering rules:
- Routers validate input (Pydantic), resolve the current user, call ONE service
  method, and return a schema. No SQL or business rules in routers.
- Every service method that touches a complaint receives the current user and
  calls the central authorization functions (core/permissions.py and
  services/visibility.py). Authorization is enforced in the backend only; the
  frontend merely hides controls based on server-provided `allowed_actions`.
- Business write + status_history/assignment rows + notifications + audit record
  are written in the SAME database transaction (all-or-nothing).
- ACCESS_DENIED and failed-login audit rows are written in a SEPARATE session so
  they persist even though the request transaction is rolled back.
- Time: store timestamps as timestamptz (UTC). "Today" for dates, overdue and
  aging is computed in APP_TIMEZONE (default Asia/Kolkata) via core/clock.py.
  Clock is injectable so tests can fix "now".
- Errors use one envelope:
  {"error":{"code":"...","message":"...","details":{...},"request_id":"..."}}
  Codes: UNAUTHENTICATED(401), INVALID_CREDENTIALS(401), ACCOUNT_LOCKED(423),
  FORBIDDEN(403), NOT_FOUND(404), VALIDATION_ERROR(422),
  INVALID_STATUS_TRANSITION(409), VERSION_CONFLICT(409), CONFLICT(409),
  INTERNAL_ERROR(500; never leak stack traces).
- Pagination: query `page` (default 1), `page_size` (default 20, max 100);
  response {"items":[...],"total":n,"page":p,"page_size":s}.
- OpenAPI docs at /docs and /openapi.json only when APP_ENV != production.

## 6. AUTHENTICATION AND ROLE-BASED AUTHORIZATION
================================================================================
Authentication
- POST /auth/login {email, password} -> {access_token, token_type:"bearer",
  expires_in, user}. JWT HS256, claims: sub (user id), role, iat, exp.
  Lifetime ACCESS_TOKEN_EXPIRE_MINUTES (default 60). No refresh token in the
  prototype; on expiry the frontend redirects to login.
- Passwords: argon2id; minimum 10 characters; (change-password enforces it).
- Lockout: 5 consecutive failures -> locked_until = now + 15 min (423
  ACCOUNT_LOCKED); successful login resets the counter. Login errors are generic
  ("Invalid email or password"). Both outcomes are audited.
- Every authenticated request loads the user from the DB; deactivated users are
  rejected immediately (401) even with a valid token.
- GET /auth/me, POST /auth/logout (audit only; client discards token),
  POST /auth/change-password {current_password, new_password}.
- Frontend stores the token in sessionStorage and attaches it to every request;
  401 -> clear session, redirect to /login; 403 -> /unauthorized or inline
  permission error. Record the XSS trade-off vs httpOnly cookies in DECISIONS.md.

DEFINITIONS
- "Participates" (FULL access): the user's bureau has an ACTIVE case_assignments
  row (PRIMARY or PARTICIPATING) for the complaint.
- "Primary bureau": user's bureau holds the active PRIMARY row.
- SUMMARY access: any authenticated user may see summary-level fields of any
  complaint: reference_number, institution, category, priority, status,
  primary bureau, participating bureau codes, received_date, target_date,
  is_overdue, days_overdue, escalation flags, updated_at. RESTRICTED fields
  (title, description, complainant_*, incident_*, resolution_summary, notes,
  status-history remarks, owner name, complaint-scoped audit trail) are returned
  as null / omitted when access_level = SUMMARY. Rationale (DECISIONS.md): bureaus
  must see that another bureau is handling the same institution to avoid
  duplicated work, but not each other's sensitive case content.
- Aggregate dashboard counts are visible to all roles (no complaint content).

Rules
- Non-primary participating officials may read the complaint and add notes but
  cannot change fields, status, ownership, or participants.
- Official may assign owner only to an active user of their own bureau.
- Official-created complaints default primary_bureau = creator's bureau and
  owner = creator. Supervisors must supply primary_bureau_id (owner optional).
  Officials cannot create a complaint with another bureau as primary.
- Implement `compute_allowed_actions(user, complaint)` once and reuse it both to
  authorize mutations and to return `allowed_actions` in complaint responses.
- Unauthorized mutations return 403 with an audit row (outcome DENIED,
  action ACCESS_DENIED, details = attempted operation). Detail endpoints that are
  restricted (notes, complaint audit trail) return 403 for SUMMARY access.
- A parametrized test iterates role x endpoint and asserts the matrix.

  received_date), primary_bureau_id (required for Supervisor only), owner_user_id?.
- Server actions in ONE transaction: generate reference number; insert complaint
  with status REGISTERED and normalized keywords; insert PRIMARY assignment;
  insert status_history (from null -> REGISTERED); run duplicate detection and
  persist SUGGESTED relations; create notifications; write audit
  COMPLAINT_CREATED. Response includes the complaint plus `related_candidates`.
- Preview: POST /complaints/related-preview {institution_id, category, title,
  description, incident_reference?, incident_date?, received_date?} returns
  candidates WITHOUT persisting anything, so the create form can warn the user
  before submit. Preview result is not authoritative; creation re-runs detection.

Editing (PATCH /complaints/{id}) requires `version` (optimistic locking -> 409
VERSION_CONFLICT on mismatch). Editable: title, description, category, priority,
source_channel, complainant_*, incident_*, target_date. Changing target_date
requires `target_date_change_reason` (stored in audit details). Editing a CLOSED
complaint is rejected (must reopen first). Editing category/title/description/
incident fields re-runs detection (adds new SUGGESTED relations only; never
modifies reviewed ones). priority/received_date edits do not alter target_date
automatically.

Listing (GET /complaints): filters q (reference/title for FULL-access rows,
reference only for SUMMARY rows), institution_id, status (multi), category,
priority, primary_bureau_id, participating_bureau_id, owner_user_id,
unassigned_owner (bool), overdue (bool), escalated (bool), received_from/to,
scope=bureau|all (officials default `bureau` = complaints where their bureau
participates; `all` returns all complaints with access_level per row; Supervisor/
Admin default `all`), sort (received_date, target_date, updated_at, priority,
days_overdue) + order. Rows carry access_level; restricted fields are null.

Detail (GET /complaints/{id}): returns the complaint payload:
  id, reference_number, institution{id,code,name}, title, description, category,
  priority, status, source_channel, complainant_type, complainant_name,
  complainant_contact, incident_reference, incident_date, received_date,
  target_date, is_overdue, days_overdue, escalation_recommended, escalation_level,
  escalation_reason, primary_bureau{id,code,name}, owner{id,full_name}|null,
  participating_bureaus[{id,code,name}], resolution_summary, resolved_at,
  closed_at, reopened_count, created_by{id,full_name}, created_at, updated_at,
  version, access_level (FULL|SUMMARY), allowed_actions{can_edit, can_add_note,
  can_manage_participants, can_change_owner, can_transfer_primary,
  allowed_status_transitions[], can_escalate, can_review_relations}.
Related data endpoints: notes, status history, assignments, relations, audit trail.
Status history and assignment history are visible at SUMMARY level (remarks

## 10. DUPLICATE AND RELATED COMPLAINT DETECTION
================================================================================
Deterministic, explainable, no external API. Implement as pure functions in
services/relations/ (normalizer.py, scorer.py) plus a persistence service.
ALGORITHM_VERSION = "1.0". Constants live in one config module and are unit-tested.

Candidate selection: all other complaints with the SAME institution_id (any status,
including RESOLVED/CLOSED; flag status in output). Complaints of other
institutions are never candidates.

Normalization:
- Unicode NFKC, lowercase, replace non-alphanumerics with spaces, drop tokens
  shorter than 3 chars, drop pure numbers, remove stopwords (standard English list
  plus: institute, institution, college, university, complaint, complainant,
  student, students, regarding, against, please), apply a simple deterministic
  suffix stemmer (ies->y, sses->ss, then strip ing/ed/es/s/ly/ment when the
  remaining stem has >= 4 chars). Text = title + " " + description.
- Keep token multiset (for TF) and token set. Store the top 15 tokens by
  frequency (ties alphabetical) in complaints.keywords.

Score (integer 0-100) = sum of components:
1. category_match: 25 if categories equal, else 0.
2. text_similarity: round(40 * (0.5 * Jaccard(token sets) + 0.5 * cosine(
   sublinear TF vectors using 1 + ln(tf)))). 
3. domain_terms: 15 * min(1, shared_domain_terms / 3). DOMAIN_TERMS (stemmed)
   include: fee, refund, tuition, hostel, scholarship, admission, cancel, seat,
   capitation, faculty, salary, qualification, recruit, laboratory, lab,
   infrastructure, library, building, approval, affiliation, extension,
   accreditation, intake, fake, forged, certificate, degree, exam, examination,
   result, harassment, ragging, safety, placement, bond, documents, original,
   withheld, deposit.
4. incident_reference: 10 if both incident_reference values are non-empty and equal
   after trim+lowercase.
5. date_proximity: using incident_date when both present, else received_date;
   gap <= 7 days -> 10; <= 30 -> 6; <= 90 -> 3; else 0.
Rules: suggest when score >= 40 AND (category_match OR text_similarity points
>= 12 OR incident_reference match). An incident_reference match always yields a
suggestion with score floored to 40. Confidence: HIGH if score >= 60 else MEDIUM.
Return at most 10 candidates ordered by score desc, received_date desc, id.

Explanation JSON (stored in complaint_relations.explanation and returned):
  {algorithm_version, score, confidence,
   components:[{name, points, max_points, detail}],
   shared_keywords:[...up to 10], shared_domain_terms:[...],
   category_match:bool, incident_reference_match:bool,
   date_gap_days:int|null, candidate_status, candidate_primary_bureau}.
The UI renders this as a human-readable "Why this was flagged" card. Shared
keywords appear in both complaints, so showing them does not leak restricted text.

Workflow
- On create/material edit: persist a SUGGESTED relation per new candidate
  (skip pairs that already have any relation row, so DISMISSED stays dismissed).
  Notify owners (or primary-bureau officials if no owner) of both complaints:
  type RELATED_SUGGESTED.
- GET /complaints/{id}/relations (all relation rows involving the complaint, with
  the other complaint at its access level) and GET /relations?status=SUGGESTED&
  institution_id=... (review queue, scoped as in the matrix).
- POST /complaints/{id}/detect-related re-runs detection idempotently.
- POST /relations/{id}/confirm {relation_type: SAME_ISSUE|RELATED_ISSUE, note?,
  add_participating_bureaus?} and POST /relations/{id}/dismiss {note (required)}.
  Allowed from SUGGESTED only; a second review attempt returns 409.
  POST /relations/{id}/revert {status: CONFIRMED|DISMISSED, note (required)} -
  Supervisor only; flips a reviewed relation (does NOT auto-remove participants;
  say so in the UI).
- Never auto-merge, delete, close, or change status of any complaint based on
  similarity. Relations are links only.
- Audit: RELATION_SUGGESTED (system actor), RELATION_CONFIRMED, RELATION_DISMISSED,
  RELATION_REVERTED.

## 11. STATUS LIFECYCLE AND AUDIT HISTORY
================================================================================
Statuses: REGISTERED, UNDER_REVIEW, ACTION_INITIATED, PENDING_INFORMATION,
RESOLVED, CLOSED, REOPENED.

Valid transitions (everything else -> 409 INVALID_STATUS_TRANSITION):
  REGISTERED          -> UNDER_REVIEW
  UNDER_REVIEW        -> ACTION_INITIATED | PENDING_INFORMATION | RESOLVED
  ACTION_INITIATED    -> UNDER_REVIEW | PENDING_INFORMATION | RESOLVED
  PENDING_INFORMATION -> UNDER_REVIEW | ACTION_INITIATED
  RESOLVED            -> CLOSED (Supervisor only) | REOPENED
  CLOSED              -> REOPENED (Supervisor only)
  REOPENED            -> UNDER_REVIEW | ACTION_INITIATED | PENDING_INFORMATION | RESOLVED
Invalid examples that MUST be tested: REGISTERED->RESOLVED, REGISTERED->CLOSED,
UNDER_REVIEW->CLOSED, CLOSED->RESOLVED, PENDING_INFORMATION->RESOLVED,
same-status transitions.

POST /complaints/{id}/status {to_status, remark?, resolution_summary?,
expected_status?, version?}
- Locks the complaint row (SELECT ... FOR UPDATE), validates the transition and
  role permission, applies side effects:
  RESOLVED: requires resolution_summary (>=20 chars) and remark; sets resolved_at.
  CLOSED: requires remark; sets closed_at.
  REOPENED: requires remark (>=5); increments reopened_count; clears resolved_at/
  closed_at; if target_date is past, requires a new target_date in the request.
  PENDING_INFORMATION: requires remark.
- If expected_status is supplied and differs from current -> 409 VERSION_CONFLICT.
- Inserts status_history; bumps version; notifies; writes audit
  COMPLAINT_STATUS_CHANGED with before/after.

Escalation: POST /complaints/{id}/escalate {reason (required)} - allowed while
OPEN and escalation_level = 0; sets escalation_level=1, escalated_at/by/reason,
adds an ESCALATION_NOTE, notifies supervisors and the owner, audits
COMPLAINT_ESCALATED. Supervisor may clear it via PATCH-like endpoint
POST /complaints/{id}/clear-escalation {note}.

Notes: POST/GET /complaints/{id}/notes (ACTION_NOTE, COORDINATION_NOTE).

Audit actions (use exactly these names): AUTH_LOGIN_SUCCESS, AUTH_LOGIN_FAILED,
AUTH_LOGOUT, AUTH_PASSWORD_CHANGED, USER_CREATED, USER_UPDATED, USER_DEACTIVATED,
USER_ACTIVATED, USER_PASSWORD_RESET, INSTITUTION_CREATED, INSTITUTION_UPDATED,
INSTITUTION_DEACTIVATED, INSTITUTION_ACTIVATED, COMPLAINT_CREATED, COMPLAINT_UPDATED,
COMPLAINT_STATUS_CHANGED, COMPLAINT_NOTE_ADDED, COMPLAINT_ESCALATED,
COMPLAINT_ESCALATION_CLEARED, ASSIGNMENT_PARTICIPANT_ADDED,
ASSIGNMENT_PARTICIPANT_REMOVED, ASSIGNMENT_PRIMARY_TRANSFERRED,
ASSIGNMENT_OWNER_CHANGED, RELATION_SUGGESTED, RELATION_CONFIRMED,
RELATION_DISMISSED, RELATION_REVERTED, REPORT_EXPORTED, OVERDUE_SCAN_RUN,
ACCESS_DENIED, SEED_RUN.
Each audit row: actor, role, entity, complaint/institution ids, before/after,
request_id, ip, outcome. GET /audit-logs (Admin, Supervisor) with filters actor,
action, entity_type, complaint_id, institution_id, outcome, date range, paginated.
GET /complaints/{id}/audit (FULL access) returns that complaint's audit rows.

## 12. NOTIFICATIONS AND OVERDUE MONITORING
================================================================================
Notification types and recipients (never notify the actor about their own action;
only active users; one row per recipient):
- COMPLAINT_ASSIGNED: new owner; if the primary bureau changed, all active
  officials of the new primary bureau.
- PARTICIPATION_ADDED: all active officials of the added bureau, plus owner.
- OWNERSHIP_CHANGED: new owner and previous owner.
- STATUS_CHANGED: owner, creator, all active officials of participating bureaus;
  plus all Supervisors when the new status is RESOLVED, REOPENED, or CLOSED.
- RELATED_SUGGESTED: owner (or primary-bureau officials if no owner) of both
  complaints.
- RELATION_CONFIRMED / RELATION_DISMISSED: owners of both complaints.
- OVERDUE: owner (or primary-bureau officials if no owner) and all Supervisors.
- ESCALATION_RECOMMENDED: all Supervisors.
- ESCALATED: all Supervisors and the owner.
Endpoints: GET /notifications?unread=&type=&page, GET /notifications/unread-count,
POST /notifications/{id}/read, POST /notifications/read-all. Users can only
read/modify their own notifications (others -> 404).

Overdue scan (jobs/overdue_scan.py)
- Finds OPEN complaints with target_date < today. Creates OVERDUE notifications
  keyed by dedupe_key "OVERDUE:<complaint_id>:<target_date>:<user_id>", and
  ESCALATION_RECOMMENDED keyed "ESCRECO:<complaint_id>:<target_date>:<user_id>"
  when escalation_recommended is true. Re-running creates NO duplicates
  (INSERT ... ON CONFLICT DO NOTHING). Writes one OVERDUE_SCAN_RUN audit row with
  counts. If the target_date is extended, new dedupe keys apply naturally.
- Triggered by APScheduler every OVERDUE_SCAN_INTERVAL_MINUTES (default 15) when
  ENABLE_SCHEDULER=true, by `python -m app.cli overdue-scan`, by
  POST /system/jobs/overdue-scan (Admin/Supervisor), and once at startup.
- Overdue/escalation indicators are ALSO computed live at query time, so
  correctness never depends on the job having run.
- Frontend: top-bar bell with unread badge (poll every 30 s via TanStack Query),
  /notifications page with mark-read, mark-all-read, filter, and deep links to
  the complaint/institution.
